### COLLECTION ACCESS BUG
------------------------------------------------------------
  save_doctors_recommendation (POST /save-doctors-recommendation) calls:
    tumor_board_collection.insert_one(insert_data)
  with no `await`. tumor_board_collection lives on the async Motor client,
  so this returns an unawaited coroutine - the insert is silently never
  executed (aside from a RuntimeWarning at runtime) and the endpoint still
  returns a "saved successfully" message. doctor_referrals_collection's
  insert_one calls elsewhere in the file ARE awaited correctly, so this
  is a one-off mistake rather than a file-wide pattern.

### PATIENT VITALS  (4 active endpoints, +1 dead - 3-way function name collision)
------------------------------------------------------------
  NOTE: get_patient_vitals is defined as a Python function name THREE
  separate times in this file (once here, once further down under
  "Alwin Section", once as get_patient_vitals_v2's twin). Each redefinition
  overwrites the previous one in the module namespace. FastAPI still
  routes correctly because each @router decorator captured its own
  function object at decoration time, but auto-generated OpenAPI
  operationIds and any code that does `from data import get_patient_vitals`
  will only ever get the LAST definition. Worth renaming for clarity.

  POST /save_patient_vitals
         function : save_patient_vitals
         does     : Looks up patient_id from sys_user_id, validates the
                    appointment_id exists and its doctor_id matches the
                    latest vitals entry's doctor_id, upserts vitals keyed
                    by a Mongo-safe timestamp, then fires three side
                    effects: (1) blocking call to the feature-context LLM
                    endpoint (hard-fails the request on non-200), (2) a
                    "temp save" call that only logs on failure, (3) a
                    Celery task dispatch that only logs on failure
         touches  : patient_user_collection, patient_appointments_collection,
                    patient_vitals_collection

  GET  /get_patient_vitals/{sys_user_id}
         function : get_patient_vitals  (1st definition)
         does     : Returns the raw vitals_doc exactly as stored, no
                    reshaping. 404 if none found
         touches  : patient_vitals_collection

  DELETE /delete_all_vitals
         function : delete_all_vitals
         does     : Deletes ALL documents in patient_vitals_collection.
                    Requires ?confirm=true or returns 400
         touches  : patient_vitals_collection
         note     : no auth/role check visible in this file guarding this
                    destructive endpoint

  GET  /get_patient_vitals/{patient_id}/{doctor_id}
         function : get_patient_vitals  (2nd definition, under
                    "########...Alwin Section...########" comment)
         does     : Same doc lookup as above, but filters entries to only
                    the given doctor_id and reshapes into a list of
                    {date, vital_data} (date split off the timestamp;
                    vital_data keeps doctor_id inside, unlike the v2 route)
         touches  : patient_vitals_collection

  GET  /get_patient_vitals_v2/{patient_id}
         function : get_patient_vitals  (3rd definition)
         does     : Same reshape into {date, vital_data} list, but across
                    ALL doctors (no doctor_id filter) and explicitly strips
                    doctor_id out of each vital_data entry before returning
         touches  : patient_vitals_collection

  DEAD: a commented-out GET /get_patient_vitals/{patient_id} sits between
  the 1st definition and delete_all_vitals - an older list-shaped response
  (id/dictation_id stringified, no date-grouping) that predates the v2/
  Alwin-section reshaping logic.
